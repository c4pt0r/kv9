# WorkSignal repeated-notification review

Verdict: no local correctness blocker in the proposed condition `!state.stopped && !state.pending`, with the existing mutex, one owner, clear-before-drain order and producer publication contract unchanged. This is a conditional source argument, not an executed test/proof or a performance result. Reviewed clean source is `57ff6851e40ed63c837189d6eb0a11190704725a`; exact file hashes are in `sources.json`.

## Local invariant and progress argument

Let P be the mutex-protected pending bit and S the terminal stopped bit. The only live-owner consumption is `begin_turn`: clear P, release the signal mutex, then inspect the real queues/state. `wait_until` never clears P and only waits while both P and S are false. The candidate preserves every P/S state transition; it removes only a condition-variable notification when P was already true. Notifications are hints, with no admission, quorum, persistence, applied-receipt or deadline authority.

1. **Publication before signal acquisition.** Queue insertion, peer mutation or receiver closure precedes `notify` taking the signal mutex. If that acquisition precedes the next `begin_turn`, publication precedes that turn's subsequent queue inspection. Mutex unlock/acquire ordering remains even when P was already true and no condition-variable call occurs. The work structures also retain their own locks/atomics. If publication happens before `begin_turn` but its delayed notify comes afterward, the notification may request an unnecessary extra turn; it cannot conceal the work.
2. **Publication during or after a drain.** If the producer takes the signal mutex after that turn's `begin_turn`, it sets or preserves P=true. The owner cannot park at its following `wait_until`. If a later `begin_turn` consumes that bit before this producer acquires the mutex, the producer sees false and performs a fresh false-to-true notification. No producer clears P. Bounded prefixes still arrange their existing next-turn hint; deferred admission deliberately waits for real work/ticks as before.
3. **Parking boundary.** If notify wins the mutex first, the owner observes P and does not wait. If the owner wins with P=false, Condvar waiting atomically releases the mutex and enters the wait; the producer then sees false, sets true and notifies. If the owner is already awakened but has not reacquired the mutex, additional producers may skip their notifications, because P remains true until that same owner resumes and consumes it. A missing waiter at a notification instant is harmless: the persistent predicate, not a counted notification, controls parking.
4. **Multiple producers.** Their signal-lock acquisitions serialize. Any number of published items may share one true P, provided the next owner turn inspects real work and preserved prefixes request another turn. This is already a Boolean work hint, not one wake per item. Queue capacity, ordering and refusal rules are unchanged.
5. **Stop and spurious wakes.** `stop` still sets S under the mutex and unconditionally notifies all. Notify after stop is ignored in both versions; begin_turn cannot revive the owner. Spurious wakeups merely repeat the loop against P/S and the original absolute tick deadline. They cannot consume P or authorize work. A stop racing a live turn does not cancel that turn instantaneously in either version; the existing stop/registry-close behavior remains.

These statements require ordinary mutex/Condvar semantics, finite owner work and eventual owner scheduling. They do not establish a bounded real-time wake latency. They also require the existing one-owner rule: `NodeDriver::new` mints the unique drain token, `spawn` rejects a second background owner through its CAS, and manual `step` uses the pump gate without clearing P. Multiple independent consumers of the same Boolean/notify_one signal would invalidate the argument; that is not a new supported use. Work locks are not acquired while holding the signal mutex.

## Producer and caller inventory

- `RaftInbox::send` publishes under its own mutex, releases it, then notifies. `set_signal` covers pre-assembly items; bounded `drain` notifies on a retained suffix. All built-in InProc/TCP/gRPC transports bind this inbox signal. The trait's default no-op binding explicitly permits periodic custom harness transports; this change adds no stronger guarantee for them.
- `RaftPeer` read-index admission, proposals, config proposals and campaigns release the peer mutex before notify. The test-only transfer-leader expression releases its temporary guard before notify.
- Async read registration publishes the queued request first; read and apply ticket Drop close the receiver before notify. Apply registration releases its registry lock before notify, including apply-before-registration. Read retained-prefix rescheduling retains its existing deferred-admission rule.
- Driver end-of-turn notifications cover newly admissible queued reads and pending Ready successors. Test-only apply pause changes its flag first. Driver stop and both poison paths retain their unconditional signal stop notification. CompletionSignal is a different multi-waiter generation mechanism and must remain unchanged.

## Existing coverage and one focused gap

`work::tests::notification_survives_drain_and_coalescing_and_cannot_restart_a_stopped_owner` checks Boolean transitions but runs sequentially; its comment does not itself create concurrent draining. `inbox_bounds_and_retained_prefix_force_another_turn` exercises actual bounded-prefix delivery and rescheduling. The real `parked_owner_serves_a_read_before_its_next_tick_and_refuses_a_second_owner` uses the under-lock park observer and a 60-second tick versus a 2-second read bound. `transport_and_campaign_wake_every_voter_without_election_tick_polling` covers actual three-owner transport delivery. `async_apply_registration_after_publication_wakes_an_idle_owner` tests post-apply registration wakeup. `deferred_admission_has_a_finite_turn_and_does_not_self_spin` and `full_credit_owner_parks_and_confirmation_wakes_without_tick` test real parking, no self-spin and quorum-triggered resumption. Their assertions remain relevant; no tests were executed for this review.

At most one new test is justified: **`concurrent_inbox_publication_survives_drain_to_park_boundary`**. Use the real WorkSignal/RaftInbox with one owner thread and channel handshakes. After consuming initial work, hold the owner *after an actual inbox drain and before wait_until*. Concurrent producers publish uniquely tagged messages and complete their notify calls while it is held (more than one drain prefix, but below capacity). Release the owner, require all messages delivered once and in each producer's order before a distant tick/deadline, then observe an actual idle park and require stop to release it promptly. This forces repeated notifications with P already true and publication missed by the previous drain, while checking real delivery rather than notification counts. Always stop/release gates and join owned threads before asserting an observation timeout. Existing parked-owner coverage supplies the complementary publish-at-atomic-park case; avoid a separate instrumentation/counting campaign.

## Algorithmic and evidence limits

The optimization removes repeated Condvar::notify_one calls while work is already pending. It does **not** remove any producer mutex acquisition, publication, queue operation, owner turn required by pending work, or completion-channel wake. At light load where each producer observes false, the new branch suppresses nothing. At high load it may reduce redundant synchronization calls, but the Boolean coalescing algorithm was already present; no group-amortization, scheduling-latency or throughput improvement follows from this review. Historical scheduling/futex profile evidence does not attribute a measured cost to these particular redundant calls. Measure the frozen candidate before selecting it.
