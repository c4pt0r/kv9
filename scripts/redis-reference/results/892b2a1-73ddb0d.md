## Outcome certainty and residual work

Both revisions recorded zero UnknownWrite, admission refusal, NotLeader refusal, read failure or client rejection in measured calls. Every after-verification snapshot had zero queued, running and in-flight backend jobs and encoded-byte reservations. These are asynchronous observations, not an atomic quiescence guarantee.

UnknownWrite means the client did not establish the outcome; it is not proof that the write failed. Configured client concurrency does not bound outstanding backend jobs after caller cancellation. After snapshots are captured after client drain and final verification; they are not atomic across nodes. Trials use the same persistent KV9 fixture, so retained background work can affect subsequent trials. A fast-refusal population can dominate aggregate terminal latency; acknowledged latency must be reported separately.

## CPU, memory and interpretation limits

At concurrency 64, the candidate read client used 1.098–1.105 CPU cores out of its two allowed CPUs; its busiest thread stayed below 0.550 cores. The three database processes together used 3.513–3.516 cores out of four allowed CPUs, versus 3.590–3.603 for Ready. The Redis client used 1.355–1.564 cores across the three mixes, with its busiest thread below 0.781 cores; its server used approximately one core. Both clients retained CPU headroom under this protocol. Lower aggregate server CPU with lower throughput does not by itself establish improved per-call CPU cost or a causal explanation for the change.

Candidate pure-write trials used only 0.026–0.036 client cores and 0.162–0.181 aggregate server cores at concurrency 64. Existing durable storage waiting still dominates this workload's low CPU utilization; the retained stage sample below is context, not evidence that this read-only representation change alters persistence semantics. Root compilation, runtime stress fixtures and archive compression were deferred during the measured matrix. Other host activity and physical-core sharing were not isolated.

The candidate replaces up to 1,024 retained receipt comparisons with tree lookup by exact context, preserving first retained duplicate match and FIFO eviction. Its source document `docs/READ-RECEIPT-INDEX.md` states the representation argument and allocation tradeoff: the tree owns an additional copy of each distinct retained context and adds tree/FIFO bookkeeping. The entry bound is not a complete process-byte bound. Per-process peak RSS is retained in every trial; for example, the candidate leader's concurrency-64 GET peaks were 24,809,472 and 27,451,392 bytes versus 25,133,056 and 28,868,608 for Ready. These process-wide peaks include accumulated fixture state, allocator behavior and prior trials; they do not isolate the receipt container's memory overhead or demonstrate that the extra index is free.

The asymptotic lookup improvement has not translated into a demonstrated throughput gain in this test. Profiling and more isolated repeated measurements are needed before making that performance claim. Two short repetitions are not a sustained-capacity estimate. The earlier volatile tmpfs diagnostic is separate and is excluded from every table in this durable comparison.
