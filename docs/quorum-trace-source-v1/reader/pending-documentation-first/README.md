# Process-local quorum trace reader — awaiting source freeze

`read_trace.py` reads exactly one `quorum-trace.json` and an independently supplied expected identity JSON. It has no server, subprocess, network, Cargo or codec invocation. Input and output are bounded to 64 MiB; the trace has at most 65,536 events. Paths must identify regular non-symlink input files, input metadata must remain stable, duplicate JSON keys are rejected, and output must be fresh. The reader records exact input byte hashes. It is a trace schema/correlation reader, not a replacement for the fixture's source/build/process/runtime audit.

The expected identity has exactly `node_id`, `process_id`, `exporter_created_unix_ns`, `process_start_ticks`, and `boot_id`. Unix-nanosecond fields are decimal **strings**, matching the Rust exporter. Although the export permits missing OS identity, accepted attribution requires an actual start tick and boot ID equal to the independently captured identity. `identity.synthetic.json` is only an explicit synthetic example, never a live binding. The reader cannot establish provenance from an identity file copied blindly from the same trace.

The v1 trace contains the exact 23-name `stage_names` vector. Each stage must satisfy `selected = recorded + contended + poisoned + full + exhausted`, and recorded counts must equal retained events. Offered must be at least selected; selected-ticket continuation stages additionally have offered equal selected. There is **no** `ceil(offered/256)` assertion: selection depends on the final eight context bytes modulo 256, repeated contexts stay selected, and continuation observations exist only for minted selected tickets. Offers count eligible observer invocations, not every Raft message or actual read request.

Ticket spans require one origin, consistent complete message key, identical local route and at most one terminal queue stage. Route IDs refer to retained local allocations, not wire/connection/generation IDs. Missing/conflicting ticket identity blocks its spans and associated context-level message timing. OutboundAccepted may race after OutboundDequeued: a reversed span is unavailable, never clamped to zero; Offered→Dequeued can remain usable. Equal observed nanosecond timestamps retain a measured zero with `timestamp_tie=true`. Missing endpoints have no duration sample. Storage event order need not be monotonic because timestamp capture precedes the observer lock; event ordinal and local timestamps are preserved.

Message correlation uses context, observed term, directed node pair and kind within this single process. Different followers are separate edges. Repeated heartbeat or response stage counts on one edge make the observed leader cycle ambiguous; the reader never selects the first match. A unique local dequeued→response-validated interval is a candidate observation, not network-only RTT or proof of a wire message's identity. Follower validated→driver-step and driver-step→response-offered spans stay separate. Response-only and missing endpoint prefixes are retained as unmatched. No time from another process is accepted or subtracted.

Groups retain their own event counts and member-observation sums per stage. They do not invent a term: a term is joined only when the context has exactly one observed message term and no observation loss. Local group spans may still have an explicitly unobserved term. `complete_group_chain_timing` denotes unique, ordered submit/admit/confirm/eligibility observations with consistent read index. `complete_context_timing` additionally requires unique usable local message edges and an observed term; neither flag means a Raft/Rust refinement proof, every peer reply, or successful client delivery. CompletionEligible is registry selection, not a client response. Deferred/repeated group attempts remain ambiguous. Member observations must not be summed across stages or used as a fabricated per-client latency weight.

Any selected observation loss in **any** stage disables context/message timing attribution and term joining for that process capture. Exact ticket-local observed spans may remain, explicitly marked partial. Saturated/invalid counter accounting rejects the input. A one-shot capture closes the observer, not the process, network or protocol queues. Pending tickets and unmatched prefixes/suffixes remain unknown; no shutdown or quiescence is inferred.

Distributions use exact integer sums/counts and sparse raw-count buckets with the existing 64-subdivision power-of-two convention. Quantiles are rank-selected bucket intervals; means use sum/count. No percentile averaging or stage-mean subtraction/addition. Empty distributions have null mean/quantiles rather than zero latency. Spans overlap and are not an additive request decomposition.
